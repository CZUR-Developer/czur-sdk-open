# SDK Admin 管理站功能设计文档

> 状态：设计稿 v1
>
> 适用范围：`sdk_app` 管理站 `http://127.0.0.1:17080/`
>
> 关联文档：`SDK_INTERNAL_ARCH_PLAN.md`、`Plugin_Capability.md`、`SDK_Auth_Error_Code.md`
>
> 最后更新：2026-04-02

## 1. 文档目标

本文档用于定义 `sdk_app` 管理站的功能设计，供后续网页 UI 设计、前端实现、后端接口补充时统一参考。

管理站不是对外能力调用入口，而是面向内部开发、测试、实施人员的运行态观测与诊断站点，重点解决以下问题：

- 查看 `sdk_app` 是否正常运行
- 查看四个网络入口的状态与端口信息
- 查看 WebSocket 服务运行情况与连接统计
- 查看当前系统、Provider、能力注册与鉴权上下文
- 查看诊断日志、错误信息和链路追踪信息
- 为 Demo 站、第三方接入调试提供状态支撑

## 2. 站点定位

### 2.1 目标用户

- 开发人员：排查协议、Provider、服务装配问题
- QA 测试人员：验证端口、能力开放状态、错误码和日志链路
- 实施/交付人员：确认 SDK 服务是否可用、授权是否正确、设备链路是否正常

### 2.2 站点目标

- 提供 `sdk_app` 的统一运行态总览
- 将 HTTP / WS / Provider / 鉴权 / 日志等分散信息集中到同一站点
- 支持“先观测、再定位、后联调”的排障路径

### 2.3 非目标

- 不承担复杂业务执行流程
- 不替代 Demo 站的能力演示功能
- 不直接暴露私有库内部结构或调试开关
- v1 不设计公网访问、多租户管理、权限分级后台

## 3. 当前实现边界与设计原则

### 3.1 当前实现基线

基于当前仓库代码，管理站设计需要显式区分“已具备的运行数据”和“后续建议补齐的数据”。

当前已可稳定依赖的数据来源：

- HTTP 管理站静态站点托管
- `GET /api/status`
- `system.info`
- `system.capabilities`
- 运行端口、绑定地址、进程运行状态、运行时长
- WS 指令通道统计：
  - `activeConnections`
  - `authFailed`
  - `requestCount`
- WS 视频通道统计：
  - `activeConnections`
  - `authFailed`
  - `binaryFrames`
  - `binaryBytes`
- Provider 名称信息：
  - `device`
  - `graphic`
  - `ocr`
  - `ofd`
  - `auth`

当前尚未在 runtime 中完整落地，但页面应预留的位置：

- 日志查询 API
- 连接级详情列表
- request / trace 级调用明细
- 会话列表、订阅关系列表
- 更细颗粒度的设备、任务、队列和错误聚合指标

### 3.2 设计原则

- 以运行观测为主，不把管理站做成能力操作台
- 先展示“系统是否活着”，再展示“为什么异常”
- 优先突出异常和风险状态，而不是平均态信息
- 页面结构需要支持未来补齐更多诊断接口，但 v1 先围绕现有状态字段设计
- 所有页面默认仅面向本机 `localhost` 场景

## 4. 信息架构

推荐一级导航如下：

- 总览 Dashboard
- WebSocket 服务
- 系统信息
- Provider 与能力
- 鉴权观察
- 日志中心
- 配置与端点

推荐全局固定区域如下：

- 顶部状态栏
  - 服务名称
  - 当前运行状态
  - Provider mode
  - 本机监听地址
  - 最后刷新时间
- 左侧导航栏
  - 一级页面入口
- 右上工具区
  - 手动刷新
  - 自动刷新开关
  - 复制端点信息
  - 跳转 Demo 站

## 5. 页面详细功能设计

## 5.1 总览 Dashboard

### 页面目标

在一个页面内回答“SDK 是否正常运行、端口是否正常、WS 是否有异常、当前 Provider 是否装配完成”。

### 页面模块

#### 1. 服务总览卡片区

展示四个入口的核心状态卡片：

- Admin HTTP
- Demo HTTP
- Command WS
- Video WS

每张卡片建议展示：

- 协议类型
- 地址和端口
- 当前状态：正常 / 不可用 / 未响应
- 是否需要鉴权
- 最近检查时间

#### 2. 运行态总览区

展示：

- `running`
- `uptimeSec`
- `bindHost`
- provider mode：`mock` / `private`
- 当前时间

#### 3. WS 指标区

拆成两个面板：

- 指令通道指标
  - `activeConnections`
  - `authFailed`
  - `requestCount`
- 视频通道指标
  - `activeConnections`
  - `authFailed`
  - `binaryFrames`
  - `binaryBytes`

#### 4. 异常摘要区

汇总最近值得注意的异常：

- 某个端口不可访问
- 认证失败次数异常增加
- 请求数持续为 0
- 视频通道有连接但没有帧数据
- Provider 未装配

### 交互动作

- 点击卡片进入对应详情页
- 支持 5s / 10s / 30s 自动刷新
- 可复制端口地址和 WS URL

### 异常态

- 状态接口不可访问时，页面进入“站点静态壳 + 核心数据缺失”模式
- 若 `running = false`，所有卡片显示降级态

## 5.2 WebSocket 服务页

### 页面目标

专门查看两个 WS 通道的服务状态、统计数据、连接风险和典型问题。

### 页面模块

#### 1. Command WS 面板

展示：

- 地址：`ws://127.0.0.1:17090`
- 当前连接数
- 鉴权失败次数
- 请求总数
- 最近一次状态刷新时间

建议预留未来字段：

- 平均响应耗时
- 正在处理请求数
- 最近错误码分布
- 最近 method 调用排行

#### 2. Video WS 面板

展示：

- 地址：`ws://127.0.0.1:17091`
- 当前连接数
- 鉴权失败次数
- 接收二进制帧总数
- 接收字节总量

建议预留未来字段：

- 最近帧率
- 当前订阅流数
- 最近流控制命令
- 最近元数据事件数

#### 3. 连接问题诊断面板

展示典型排障提示：

- token 不匹配
- 客户端连错端口
- 指令通道误发二进制消息
- 视频通道没有开始订阅即等待帧
- 服务已启动但页面连接目标不是 localhost

### 交互动作

- 测试连接
- 复制 WS URL
- 查看协议示例
- 跳转 Demo 站对应的调试入口

### UI 设计输入

- 左右双栏布局更适合横向比较两个 WS 服务
- 统计卡采用大数字 + 趋势标签
- 风险信息使用告警列表，不用表格

## 5.3 系统信息页

### 页面目标

展示当前 `sdk_app` 的运行环境和基础系统状态，用于确认部署、运行和排障上下文。

### 页面模块

#### 1. 基础信息区

展示：

- 服务名：`sdk_app`
- 运行状态
- 启动时长
- `bindHost`
- 端口映射

#### 2. 运行模式区

展示：

- provider mode：`mock` / `private`
- web 根目录
- 当前站点根路径

#### 3. 系统摘要区

建议设计为可扩展模块，v1 可先展示占位：

- 操作系统信息
- 主机名
- 进程 PID
- CPU / 内存占用
- 线程数

说明：

- 若这些字段当前没有 API 支撑，先在文档中定义为“扩展信息区”，UI 设计上保留布局位

### 交互动作

- 刷新状态
- 复制状态 JSON
- 导出当前系统摘要

## 5.4 Provider 与能力页

### 页面目标

清晰展示当前 SDK 装配了哪些 Provider，以及当前公开了哪些 method 和能力域。

### 页面模块

#### 1. Provider 列表区

展示以下 Provider：

- `device`
- `graphic`
- `ocr`
- `ofd`
- `auth`

每项展示：

- provider 名称
- 就绪状态
- 来源模式：mock / private / unavailable
- 关联能力域

#### 2. 能力目录区

基于 `system.capabilities` 展示 method 清单。

列表字段建议为：

- `method`
- `summary`
- `auth_scope`
- `device_scope`
- `status`
- `legacy_aliases`（如存在）

#### 3. 能力状态统计区

统计：

- `ga` 数量
- `beta` 数量
- `planned` 数量
- 当前已开放域数量

### 交互动作

- 按域过滤
- 按状态过滤
- 搜索 method
- 查看 method 详情抽屉

### method 详情抽屉内容

- method 名称
- 所属 domain
- 描述摘要
- 认证要求
- 设备范围要求
- 状态说明
- 兼容旧命令映射
- 推荐在 Demo 站的演示入口

## 5.5 鉴权观察页

### 页面目标

帮助内部人员确认授权上下文是否正确，尤其是账号等级、设备白名单、能力清单是否符合预期。

### 页面模块

#### 1. 鉴权说明区

固定说明：

- 匿名能力与受保护能力的区别
- `api_key` 与 `session_token` 的优先级
- `auth_scope` 与 `device_scope` 的含义

#### 2. 授权上下文查看区

展示 `AuthContext` 关键字段：

- `is_valid`
- `account_type`
- `account_type_code`
- `auth_scene`
- `license_mode`
- `device_scope`
- `expires_at`
- `capabilities`

#### 3. 常见授权失败区

展示错误码与释义：

- `1100 AUTH_REQUIRED`
- `1101 API_KEY_INVALID`
- `1102 API_KEY_EXPIRED`
- `1103 SESSION_TOKEN_INVALID`
- `1104 ACCOUNT_TYPE_NOT_ALLOWED`
- `1105 DEVICE_NOT_IN_AUTH_SCOPE`
- `1106 AUTH_SCENE_MISMATCH`
- `1107 CAPABILITY_NOT_GRANTED`

### 交互动作

- 输入 ApiKey 进行本地校验
- 查看返回的 `auth_context`
- 复制授权摘要

说明：

- 该页允许执行轻量诊断类请求，如 `auth.validate`
- 不承担完整接入演示流程，复杂联调仍在 Demo 站完成

## 5.6 日志中心页

### 页面目标

为问题排查提供统一日志入口，关联请求、错误码、trace_id 和站点模块。

### 页面模块

#### 1. 日志筛选栏

筛选维度建议包括：

- 时间范围
- 日志级别：`debug / info / warn / error`
- 模块：`http / ws-command / ws-video / auth / provider / system`
- 关键字
- `request_id`
- `trace_id`
- 错误码

#### 2. 日志列表区

单条日志建议展示：

- 时间
- 级别
- 模块
- 简要消息
- 关联 `request_id`
- 关联 `trace_id`

#### 3. 日志详情抽屉

展示：

- 完整日志内容
- 上下文 JSON
- 相关错误码说明
- 推荐排查动作

### v1 设计约束

- 当前代码尚未提供独立日志查询 API，页面先按产品需求设计
- UI 结构需能兼容后续日志接口补齐
- 如 v1 首期只有“最近错误摘要”，该页面可先做只读壳页

## 5.7 配置与端点页

### 页面目标

集中展示接入方需要知道的本地服务地址、端口、认证方式和调用约束。

### 页面模块

#### 1. 端点信息区

展示：

- Admin HTTP：`http://127.0.0.1:17080`
- Demo HTTP：`http://127.0.0.1:17081`
- Asset HTTP：`http://127.0.0.1:17082`
- Command WS：`ws://127.0.0.1:17090`
- Video WS：`ws://127.0.0.1:17091`

#### 2. 访问约束区

展示：

- 默认仅监听 `localhost`
- HTTP 管理接口的 Bearer Token 规则
- WS token 查询参数规则
- 指令通道与视频通道分离原则

#### 3. 快速复制区

支持复制：

- HTTP 地址
- WS 地址
- 示例请求模板
- 常用错误码链接

## 6. 全局状态与交互规则

### 6.1 全局状态定义

- 正常：服务在线，指标可拉取
- 警告：服务在线但存在异常统计或 Provider 缺失
- 异常：状态接口不可访问或关键服务离线
- 未知：首次加载前或数据未返回

### 6.2 自动刷新规则

- Dashboard：默认 5 秒
- WebSocket 服务页：默认 5 秒
- 系统信息页：默认 10 秒
- Provider 与能力页：默认手动刷新
- 日志页：默认手动刷新或 10 秒轮询

### 6.3 异常提示规则

- 所有请求失败都要显示错误码和可读文案
- 若有 `trace_id`，必须显式展示
- 网络错误与业务错误分开展示
- 对“未实现”与“无权限”要使用不同提示文案

## 7. UI 设计要求

### 7.1 视觉层级建议

- 首页突出“大状态 + 大数字”
- 详情页突出“结构化信息 + 筛选能力”
- 异常信息优先级高于说明文案

### 7.2 组件建议

- 状态卡片
- 指标卡片
- 可筛选表格
- JSON 查看器
- 日志时间线
- 详情抽屉
- 顶部全局告警条

### 7.3 标签体系建议

- `ga`：稳定可用
- `beta`：可试用，规则可能微调
- `planned`：仅协议预留，当前不可执行
- `mock`：模拟 Provider
- `private`：真实私有 Provider

## 8. 页面数据来源建议

v1 建议页面主要依赖以下数据源：

- `GET /api/status`
- `system.info`
- `system.capabilities`
- `auth.validate`
- `auth.get_context`

后续可扩展的数据源：

- 日志查询接口
- WS 连接详情接口
- 请求调用历史接口
- 错误码聚合接口

## 9. 验收标准

管理站功能设计完成后，应满足以下要求：

- UI 设计师可依据本文档直接输出后台页面结构图和高保真界面
- 开发可明确区分“v1 必须有的数据”和“后续扩展接口”
- 各页面之间职责不重叠：
  - Dashboard 负责总览
  - WebSocket 服务页负责连接与通道
  - Provider 与能力页负责能力开放视图
  - 鉴权观察页负责授权上下文
  - 日志中心负责排障信息
- 文档内容与 `sdk_app` 当前架构、端口规划、授权规则保持一致

## 10. 建议的后续补充接口

为让管理站真正具备排障价值，后续建议补齐以下接口：

- 日志查询接口
- 近 1 分钟 / 5 分钟指标快照接口
- WS 连接详情接口
- 最近错误事件接口
- Provider 健康检查接口
- 当前任务队列 / 设备会话状态接口

这些接口不影响当前 UI 设计启动，但建议在实现阶段尽早补齐。
