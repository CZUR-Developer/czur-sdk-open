# SDK Open 鸿蒙指定英文识别失败分析（2026-10-30）

本文记录旧算法库（Build ID `d6b4fc1c4bb1db871016c6cf941fc33cc9c2d84f`）的失败原因。
16:11 更换算法库为 Build ID `fdcb847a5d2f1d0ef08d8640a46d34ee14e39958` 后，
同一样本的显式 `en` 文字提取、PDF 导出及文字层校验均通过，未新增崩溃日志。
最新验证见 [重新打包验证记录](sdk_open_harmony_ocr_x86_repack_20261030.md)。
以下“当前库”等表述均指分析时使用的旧库。

## 结论与边界

指定 `language=en` 后，OCR 已进入英文识别的 SVTR / NCNN 推理路径。
2026-10-30 14:32:04 的崩溃现场表明：`ncnn::Gemm::forward` 收到的输入向量
仅包含一个 `ncnn::Mat`，但当前执行分支访问第二个元素，随后把越界数据当作
引用计数指针进行原子读写，触发 `SIGSEGV`，导致整个 AppService 退出。

后续在独立探针中沿真实 API 初始化和识别流程读取模型结构，已进一步确认：
英文实际加载 `3_2_6.model`，其中有单个动态输入、带常量参数的 Gemm 层，
而本次 OHOS 库的 Gemm 只读取参数 0～3，没有对应常量权重加载实现。
**当前英文模型与 OHOS 库内 Gemm 能力不匹配，是此次越界的明确触发条件。**
此前关于随机内存破坏、线程或 strip 的猜测不再作为首要解释。

修复需要兼容当前实现的同语义模型资源，或支持这些模型算子的 OHOS 算法构建。
当前证据还不能证明更换整份算法库是唯一途径。


用当前 `third_party_repo/czocr/lib/ohos/libczcv_ocr.so` 的 Build ID 与日志核对，
再用 OHOS LLVM 反汇编定位，避免使用其他平台或其他版本的符号解释现场。

14:32 的日志明确提示从第 2 帧起回溯不可靠，因此其中的 LayerNorm / Pooling

`czcv_ocr_recog → CZCV_DocPipeline → RecognizerSVTRImpl → NCNN → Gemm`
这一推理路径；本次输入越界结论依据 14:32 现场寄存器、内存和指令。

## 输入越界的证据

输入参数 `x1` / 保存寄存器 `x20` 指向 `std::vector<ncnn::Mat>`。
崩溃内存中的向量三个指针为：

```text
begin    = 0x0000007f8a5c11e0
end      = 0x0000007f8a5c1228
capacity = 0x0000007f8a5c1228
end - begin = 0x48 = 72 字节
```

该二进制的 Mat 复制代码使用 72 字节步长，因而向量只有一个元素。
Gemm 保存 `begin` 到 `x25`，当前分支却执行：

```asm
0xba0388: add   x8, x25, #72    // 第二个 Mat 的起始地址，已等于 end
0xba0398: ldr   x8, [x25, #80]  // 读取该 Mat 内偏移 8 的引用计数指针
0xba039c: cbz   x8, ...
0xba03a0: ldaxr w9, [x8]        // 崩溃指令：引用计数原子读取
```

现场 `[begin + 80]` 为 `0x6b6b6c3e1343d9f3`，与寄存器 `x8` 一致；
内核报告访问地址 `0x006b6c3e1343d9f3`，与忽略顶字节后的地址相符。
因此无效指针来自输入向量边界外，不只是笼统的“矩阵计算失败”。
这里仍不能反推出是哪一行模型参数或哪一处上游代码造成输入不一致。

## 进一步确认：英文模型与库内 Gemm 能力不一致

在设备临时目录运行独立原生探针，沿原 API 的 init / set_lang / recog 流程，
在模型解码返回时只读取结构元数据，没有导出权重或修改原模型。
实际 `en` 路径加载的识别模型是 `3_2_6.model`，不是按语言名称猜测的 `3_2_2.model`。
设备服务目录中的以下文件哈希已与探针使用的源文件核对：

```text
3_2_6.model
2c1ff5ea54001b14ecdb3e6754f256f2dd0f8e92bb16cd4c397c0c2a635cf7cc
6.dat
5a7180ee079d06678be9743313698e7d21fed5a808327723a3d3c992a94d3925
```

`3_2_6.model` 的 NCNN 二进制结构头有效，226 个层、233 个 blob，参数区
12,988 字节且完整解析至末尾。以下 Gemm 层的输入数均为 1：

| 层索引 | 参数 5 / 6 | 参数 8 / 9 | 参数 3 / 10 |
| --- | --- | --- | --- |
| 198 | 1 / 1 | 240 / 120 | 1 / 4 |
| 200 | 1 / 1 | 120 / 240 | 1 / 4 |
| 208 | 1 / 1 | 240 / 120 | 1 / 4 |
| 210 | 1 / 1 | 120 / 240 | 1 / 4 |
| 224 | 1 / 1 | 438 / 120 | 1 / 4 |

这些层使用常量 B / C 及其维度、广播配置；Gemm 在此约定下只有 A 是动态输入。
但本次库的实现存在以下差异：

- `Gemm::load_param` 位于 `0xba0150`，只读取参数 0、1、2、3，
  到 `0xba01c4` 已返回，没有读取参数 4～10。
- Gemm 的虚函数表中 `load_model` 指向默认 `Layer::load_model`（`0x86ac4c`），
  该函数仅返回 0，不读取常量矩阵。没有 Gemm 专用 `load_model` 实现。
- `Gemm::forward` 仍直接访问第二个动态输入，与崩溃现场只有一个输入完全对应。

同一探针的 `ch` 路径加载 `3_2_1.model`，该识别图没有 Gemm 层；公共方向模型
`3_5_1.model` 则有一个 3 输入 Gemm，仅使用参数 0～3。这解释了中文默认模式
能通过、指定英文模式却触发越界的差异。

独立探针在此错误组合下曾返回 `recog=0`、4 个块，但不构成有效识别通过：
实际算子约定仍然不匹配，越界的结果依赖进程内存状态，返回成功不能消除该缺陷。

尝试复用仓库内 loongarch64 的旧英文模型后，其图结构不同（406 层、445 个 blob，
末端分类数 97）；配套旧字典格式也不符合当前 SVTR reader。对字典做格式转换的
临时试验仍崩溃。通过公开 `czocr_set_version` 设置 `2` 或 `v2` 也仍加载 v3 路径。
这些均仅在设备临时目录试验，未进入安装包，不能作为生产修复。

## 已核对的资源及实验限制

- 用户指定的 `x86-64/3_1_1.model` 已进入包内，字节一致，SHA-256 为
  `8a04ffae2d1c565e678215b95286ab79050c2c76d56b86fbe20854835921c6c8`。
- 前一轮检查过 `3_2_2.model`、`3_1_4.model`、`2.dat` 的设备哈希；本轮补齐
  实际英文路径使用的 `3_2_6.model`、`6.dat` 校验。文件传输和释放一致，但模型
  中的 Gemm 约定与当前算法实现不兼容。
- 早先缺模型时的 `dissolve_v2` 崩溃、native 库加载失败，与当前推理越界是不同故障。
- 单线程、OpenMP 亲和性设置、禁止 strip 均未稳定解决应用内问题，不能判定为根因。
- 独立探针有成功和失败，不能据一次成功排除算法内部状态或内存问题。
- 尚无证据将问题归因于模拟器；需要实机对照才能判断是否与模拟环境有关。

## 后续定位顺序

1. 优先提供与当前库配套的英文模型及字典，或将当前英文模型重新转换为当前
   NCNN 支持的等价图；保留字符映射、输入预处理及输出约定，不能简单改文件名。
2. 若无法提供等价模型，则需要 CZOCR 的 OHOS 构建支持模型的常量 Gemm 参数及
   权重加载，核对 NCNN 转换工具与运行库的兼容性。
3. 修复后检查所有可选语种模型，防止同样的算子约定问题出现在其他语言。
4. 保持其他条件不变进行独立探针、AppService 和实机对照，验证修复后英文模式
   多次执行及中英文切换均通过。

当前仓库没有发现对应算法 / NCNN 实现源码，不能在 SDK Provider 层安全补齐该内部
算子的实现。当前状态为“模型 / 运行库能力不匹配已确认，英文尚未修复”。
